REPORT OVERVIEW

Why this project combines infrastructure and model adaptation.

SLAI T-Rex starts from one premise: better domain capability requires a training substrate that is stable, observable, and efficient enough to support controlled experiments. A trillion-parameter MoE model stresses memory capacity, pipeline balance, collective communication, and irregular operators, while an Operations Research task also requires mathematical fidelity, executable solver code, and structural equivalence. The project handles these requirements as one connected pipeline, from Ascend runtime work to the final benchmark.

The system study uses DeepSeek-V4-Pro as the large-scale workload and Ascend CloudMatrix384 SuperPOD with Ascend 910C as the execution environment. It starts from profiling rather than from an isolated optimization trick, decomposing a training step into useful computation, exposed communication, pipeline bubble, and device-side idle time. The current Pro SFT implementation organizes the response into two levels: first tune the parameters and environment of existing MindSpeed-LLM capabilities, then introduce custom fused operators and framework patches for selected computation paths.

The model study uses DeepSeek-V4-Flash as the main experimentation platform. The starting checkpoint already contains useful knowledge of common linear and mixed-integer programming templates, but its errors reveal that familiarity with optimization language is not enough. A generated program may compile while using the wrong variable domain, omit a conservation constraint, mishandle a ratio, or produce a graph that is structurally different from the reference formulation. CPT is therefore used to broaden the model's domain prior, while SFT is used to make solver-facing behavior and output contracts reliable at inference time.

This distinction also explains the organization of the open-source repository. Data construction is kept separate from MindSpeed-LLM training. The data tools create self-contained documents and instruction examples; conversion scripts turn them into the indexed format expected by training; launchers provide environment-driven recipes; kernel and framework directories expose the Ascend-specific acceleration path; evaluation scripts measure both execution and formulation structure.

SYSTEM STUDY / ASCEND SUPERPOD

The bottleneck is a chain, not a single kernel.

At trillion-parameter scale, device time is shaped by the interaction of parallelism, communication, memory, and operator implementation. The report measures these layers together so that a kernel speedup is interpreted in the context of the training step that it actually affects.

CURRENT PRO SFT

Two implementation levels, measured in three stages.

The community configuration provides the 34.85% MFU baseline. Level 1 changes only MindSpeed-LLM parameters and runtime settings, raising MFU to 36.28%. Level 2 then activates custom fused operators and framework patches, reaching 38.57%. The cumulative gain over the community baseline is 3.72 percentage points.

LEVEL 1

Use existing MindSpeed-LLM capabilities

Tune VPP, MoE All-to-All overlap, GEMM gradient-accumulation fusion, task queue behavior, HCCL settings, and the NPU memory allocator. No new operator implementation is introduced at this level.

LEVEL 2

Replace selected computation paths

Apply framework patches and load custom operator artifacts. The optimized paths cover fused SwiGLU, MoE permutation, DSA index scaling, CPU binding, SparseFlashMla, and LightningIndexer.

LEVEL 1 / 36.28% MFU

Tune the training plan before changing kernels

This level stays inside MindSpeed-LLM's existing feature set. Its purpose is to expose less communication, reduce pipeline idle time, and avoid unnecessary memory traffic without adding a new operator dependency.

Parallel and pipeline schedule

The 512-rank run uses TP=2, PP=8, EP=64, ETP=1, CP=1, and DP=32 with Sequence Parallel. Setting four layers per virtual pipeline stage introduces interleaved VPP scheduling: it shortens idle gaps between pipeline stages, while accepting more scheduling and point-to-point communication.

TP=2 · PP=8 · EP=64 · DP=32 · VPP=4 layers

Communication and gradient fusion

MoE All-to-All is overlapped with expert computation so that token dispatch is less visible on the critical path. GEMM gradient accumulation is fused into the weight-gradient calculation, removing a separate Add and repeated memory access. Distributed optimizer, full recompute, optimizer swap, and manual garbage collection keep the full-parameter run within the memory budget.

MoE overlap · GEMM grad fusion · recompute · optimizer swap

Runtime and collective settings

Task queue level 2 increases asynchronous host-to-device submission. A 256 MB HCCL buffer and topology-aware All-to-All strategy target large-message throughput, while the AIV communication path is selected for this workload. Expandable allocator segments mitigate fragmentation from dynamic tensors and communication buffers. These settings can consume more peak memory and must be revalidated when CANN or HCCL changes.

TASK_QUEUE_ENABLE=2 · HCCL_BUFFSIZE=256 · AIV
LEVEL 2 / 38.57% MFU

Replace expensive paths with fused implementations

This level adds compiled custom operators and the framework patches that route execution into them. It reduces launch overhead and intermediate memory traffic, and changes the sparse-attention path itself rather than only tuning its schedule.

MoE and activation fusion

The activation path combines value limiting, SwiGLU, routing-probability multiplication, and the corresponding backward work where applicable. MoE token permutation uses a fused mask-map path, and the DSA indexer combines two constant scales into one operation. These changes remove temporary tensors, dtype conversions, copies, and small elementwise launches.

limited SwiGLU · routing probability · MoE permute · index scaling

Sparse attention execution

LightningIndexer first selects the top 1,024 candidate positions. SparseFlashMla then computes attention only on those positions, its fused backward handles the sparse gradient path, and the fused KL-loss backward updates the indexer. The reduction in selected positions is especially valuable for long sequences, where dense attention would otherwise dominate computation and memory access.

LightningIndexer → topk=1024 → SparseFlashMla → fused backward

Integration boundary and validation

The generic FlashAttention switch and the sparse-attention switch select different paths: the latter depends on the custom operator artifacts and matching framework patches. CPU affinity is also applied per local rank to reduce process migration and NUMA jitter, but it is a runtime optimization rather than an NPU kernel. Correctness, compiler compatibility, memory use, and end-to-end MFU must all be checked together after an environment change.

General FlashAttention and DSA sparse attention use distinct execution paths.

Profiling the exposed communication

The baseline training step spends 40.76 seconds in communication, which accounts for 52.2% of total device kernel time in the reported profile. Tensor and data parallel collectives contribute the largest share, followed by pipeline point-to-point traffic. Expert-parallel AllToAllV is important for MoE token dispatch, but it is a smaller part of this particular breakdown because the SuperPOD interconnect handles that traffic comparatively well.

From parallelism to kernel execution

The system response is hierarchical. Expert-tensor parallelism reduces unnecessary tensor-parallel pressure in MoE layers while keeping the pipeline configuration stable. Load-balanced scheduling addresses uneven work between pipeline stages. Communication and computation are overlapped where the execution graph permits it, and token dispatch is organized so that synchronization does not expose avoidable idle time. The optimizer path uses memory-aware techniques, including a double-buffered swap strategy, to keep full-parameter training within device constraints.

Profiling also shows why generic operator optimization is insufficient. Sparse attention is memory- and control-bound: the vector compute pipeline remains lightly used while local-buffer movement and scalar index or gather logic dominate. By contrast, MatMul and grouped expert computation are closer to cube-compute saturation. The long tail contains many tiny Cast, Add, reshape, and copy operations. Each is short, but the repeated launch and memory traffic costs accumulate across the step, making them natural targets for fusion.

AuraKernel and full-stack fusion

AuraKernel combines a hardware-grounded harness, iterative optimization memory, parallel candidate evaluation, and solver-guided tiling search. The optimization loop first compiles and checks a candidate for correctness on real Ascend hardware. Only feasible candidates enter performance comparison. This separates mathematical or functional correctness from performance selection, and makes hardware counters useful as a diagnosis of whether a candidate is compute-bound, movement-bound, or scalar-bound.

Within Level 2, operator results are reported at two measurement scopes. AuraKernel improves already-visible bottleneck kernels, including sparse attention, the lightning indexer gradient, and weight-free RMSNorm. The fusion path changes the execution unit itself by removing eager intermediate tensors, dtype round trips, and autograd-visible boundaries. An isolated kernel speedup and a fused module speedup answer different questions, but both contribute to the final 38.57% MFU.

WHY TWO STAGES

An optimization model can run and still be wrong.

Operations Research asks a model to preserve meaning across several layers at once: a natural-language problem, a mathematical formulation, a data interface, and an executable solver program. A response that looks plausible or returns a solution is not necessarily faithful to the intended model.

The report's error analysis found that structural equivalence was the largest failure family, while protocol and API mistakes were the most visible Pass@1 failures. Other recurring problems included continuous variables used for discrete entities, incomplete conservation constraints, unit and ratio errors, and nonlinear expressions that were not solver-compatible.

28.3%

Structural equivalence

Variable families, constraint counts, and the canonical formulation graph do not match the reference.

23.9%

Protocol, API, schema

Code fences, malformed Python, unsafe indexing, or incorrect Gurobi usage block evaluation before reasoning can be scored.

12.5%

Discrete-variable semantics

Counts, assignments, vehicles, and selections need integer or binary domains instead of an LP relaxation.

CPT

Teach the domain before asking for the answer.

Continued pre-training exposes the model to OR terminology, recurring formulation families, solver-aware nonlinear reasoning, data structures, and the relationship between business requirements and mathematical constraints. It is the knowledge-infusion stage of the pipeline.

SFT

Make the knowledge appear in the required format.

Supervised fine-tuning teaches the model to follow code-only contracts, write safe Gurobi programs, handle data files and schemas, extract objective values, and produce canonical outputs without relying on few-shot demonstrations. It is the behavior-shaping stage.

DATA ENGINE

Correctness is built before tokenization.

The OR-CPT Engine treats language generation as one step inside a controlled verification path. The release keeps the data and training boundaries separate: the engine establishes mathematical fidelity and lineage, while MindSpeed tokenizes, packs, samples, and optimizes the model.

01

Verified seeds

A seed is a structured optimization instance with sets, coefficients, objective direction, variable domains, bounds, constraint families, and executable or LP artifacts. Infeasible, degenerate, unstable, or duplicated seeds are filtered before language generation.

02

Structured variation

Canonical and semantic intermediate representations make it possible to vary domains, entities, objectives, variable families, constraints, numerical ranges, and data shapes without copying the source problem. Samples are rendered as data-in-problem (DP), data-in-table (DT), or data-problem-separate (DPS).

03

Admission gates

Accepted documents pass natural-language quality checks, contract validation, static checks, independent execution, and objective comparison. Agreement on one numerical optimum is not treated as proof of symbolic equivalence, so structural checks remain necessary.

TRAINING DESIGN

CPT is selected as an initialization, not as a score by itself.

The training experiment is designed around transfer. A checkpoint is useful when it models the OR corpus better, remains numerically stable, retains general capability, and improves a later SFT run under matched conditions. This makes the CPT-to-SFT comparison more informative than comparing unrelated recipes.

A domain-dominant but retention-aware mixture

The CPT corpus combines solver-verified OR documents with collected OR resources, mathematical reasoning data, code data, and general English. The roles are deliberately different. OR documents provide formulation semantics and structural modeling patterns; mathematical data supports symbolic derivation and reformulation; code data supports executable solver implementation; general English protects broad language understanding. The report therefore treats mixture composition as a recipe parameter rather than assuming that pure domain data is always better.

The practical lesson is important for reproduction. A domain-specialized model should not be selected from OR validation loss alone. Intermediate checkpoints are checked on held-out OR likelihood, general validation signals, representative general benchmarks, and downstream OR transfer. The best checkpoint is the one that gives a useful balance across these objectives and continues to improve the next training stage.

Why the matched transfer test matters

The controlled comparison uses the same Clean-CoT SFT data, optimizer configuration, update budget, sequence length, and evaluation protocol for two routes: original checkpoint to SFT, and original checkpoint to CPT to SFT. The difference between those final models is therefore interpreted as the contribution of the CPT initialization. This design avoids attributing a gain to CPT when it may actually come from a different SFT dataset or learning-rate schedule.

The report also records a long-running 50K SFT stability run on eight nodes and 128 Ascend 910C NPUs. With global batch size 128, micro batch size 1, and sequence length 8192, the run reaches 800/800 iterations without skipped or NaN iterations. This is infrastructure evidence rather than the main quality result, but it establishes that the data conversion, MindSpeed-LLM launcher, model implementation, and Ascend environment can sustain the workflow.

What the four benchmarks measure

NL4OPT and OptiBench test natural-language-to-optimization modeling and problem understanding. B4O-Feasible checks whether the generated Gurobi program executes and produces a feasible solution. B4O-ORGEval goes one layer deeper: it evaluates structural equivalence between the generated formulation and the reference model, independently of implementation details.

Why the combination matters

Under matched SFT conditions, CPT initialization improves all four zero-shot Pass@1 scores, with the largest additional gain on B4O-ORGEval. The broader mixture also retains general capability: the report finds no sign of catastrophic forgetting, while pure-OR CPT causes a substantial drop on general benchmarks.

DATA QUALITY / SFT

Better data beats simply more synthetic data.

The report's SFT scaling experiments show a non-monotonic pattern. Increasing a similar self-distilled dataset from 10K to 50K does not automatically improve every task. The more reliable improvement comes from identifying concrete modeling mistakes, repairing them under a contract, and validating the repaired answer before export.

The cleaning targets are practical rather than stylistic. They include wrong variable types, wrong objective direction, missing capacity or demand constraints, incorrect ratio or average handling, invalid nonlinear forms, unsafe data access, and incorrect Gurobi API calls. The goal is not to make every answer longer. It is to make the modeling checkpoints visible and repeatable: choose variable domains, determine the objective, check the critical constraints, handle ratios or nonlinear terms, then implement and execute the solver model.

Clean-only repairs the answer while preserving the original reasoning style as much as possible. Clean-CoT additionally inserts a short modeling checklist into tagged responses. A cleaner proposes a repair, an independent reviewer checks whether the repair is justified, local validation executes the code and checks the output contract, and export checking verifies the final artifact. The reviewer is important because an apparently helpful repair can introduce a new inconsistency, such as turning a continuous quantity into an integer or deleting a necessary constraint.

Progressive SFT and general-capability anchoring

The report identifies a tension between solver-API syntax and natural-language modeling. A single SFT stage can let gradients from code-only targets and reasoning-rich targets interfere with one another. The proposed progressive recipe separates them. Stage I uses code-only OR targets with a conservative 5e-7 learning rate to stabilize Gurobi calls, data loading, and output contracts. Stage II continues from that checkpoint on the complete Clean-CoT 10K set with a 1e-6 learning rate, so the model can learn richer formulation behavior without losing the syntactic backbone.

The same principle applies to general capability retention. The report adds 10% to 15% general-purpose instruction data in the later SFT stage, including open-domain question answering, multi-turn dialogue, and creative writing. In CPT, the analogous lesson is to interleave OR data with mathematical, code, and general-language support data. Pure OR CPT causes a 10 to 15 point drop on general benchmarks without improving the overall OR score, so domain adaptation needs an anchor rather than an all-domain-only mixture.

SCALE-UP VALIDATION

The workflow transfers from Flash to Pro.

DeepSeek-V4-Flash is the main controlled platform for studying CPT initialization and SFT data quality. DeepSeek-V4-Pro is then used to test whether the complete OR-oriented workflow remains effective at trillion-parameter scale. The Pro result is a scale-up validation of the full pipeline, not an isolated CPT ablation.

On DeepSeek-V4-Pro, the original model starts at an average OR score of 70.16% under the reported zero-shot Pass@4 setting. SFT alone raises the average to 76.74%, while the complete SLAI T-Rex-Pro configuration reaches 77.33%. The strongest absolute movement remains on B4O-ORGEval, which rises from 43.91% for the original model to 61.93% for the complete configuration. OptiBench changes only slightly, which is a useful reminder that a single aggregate number hides different task sensitivities.

LIMITATIONS AND NEXT STEPS

The open workflow is a starting point, not a final solver.

The report is careful about what its validation proves. Matching an objective value on one numerical instance is a strong executable-consistency signal, but it is not a proof that two formulations are symbolically equivalent. Structural validation remains necessary, especially for canonical graph checks, nonlinear reformulations, ratio constraints, and quadratic terms.

The current release therefore exposes the pieces needed for inspection and reproduction while leaving room for stronger evaluators and broader data. Future work includes more diverse solver-verified corpora, better structural checks for nonlinear models, broader OR families, retention-aware curricula, and agentic reinforcement-learning workflows built on top of the verified training stack.
